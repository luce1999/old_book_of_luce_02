## 1. Player names and privacy

First, protect player privacy. By default, use a nickname instead of a player's own gaming platform name. Do not directly show the name used to log in to the platform. A fixed letter-based name plus some digits can be generated by default. Consider whether duplicate names are allowed. They may allow impersonation. It is best to forbid names that have ever been used. Even if the original owner changes their name, do not make the old name available again.

Also forbid names that are too short, invalid characters, and whitespace. There is also "xxx." This makes reporting and keeping records easier. In other words, everyone has streamer mode on by default.

To improve the game experience, I suggest preventing anger from the last match from carrying into the next. This can also be left to the map creator. Do not switch to showing someone's real name after they become a friend, because this causes confusion. xxx has this problem. The displayed name should always stay the same.

## 2. Rooms and starting a game

Next are the host's powers. In ranked mode, the platform assigns players and starts the game directly. But niche games and game lobbies usually need a host. I suggest leaving it entirely to the game creator to decide whether players can be kicked, teams can be changed, game settings can be changed, or players' own settings can be changed. The room is just a small lobby.

Rooms need no player limit, or a limit of about three times the number needed to start. Players should see which games are in progress and who is in them. Start when enough players are ready, with earlier arrivals playing first. Games such as werewolves and villagers have very uneven team sizes. Teams can be set up in the lobby, or players can set conditions. Some games are flexible about player counts, while others need strictly balanced teams. All of this needs consideration.

Do not begin immediately after the game launches. There can be an initialization stage of about 60 seconds, when the host or a player vote sets the content. Ideally, no setup is needed because the creator has already prepared it. Players can also state their preferences in the lobby, and the game starts based on them. If a player chooses "xxx," they can enter other modes. Otherwise, they can only wait.

## 3. Matching, rewards, and content

I strongly suggest two separate values: map familiarity and MMR. The first shows whether someone is still a beginner and can stop growing at a certain value. The second represents things such as wins. It does not need long-term adjustment; the last few games are enough, and it need not be very precise. Teams should mainly be random. MMR is only a reference and can even remain completely hidden.

The platform should also give reward points, like a currency. They can buy skins or unlock content, but cannot be transferred. They can also unlock titles. It is best not to give real combat power.

The platform must not force the game to pause when someone lags. This xxx design is terrible and is only somewhat useful in 1v1. Players usually have trouble coming back after lagging, so I think this design is unnecessary.

The platform should regularly give a clear place to popular content that has been reviewed by people, ideally with its code reviewed too. It should be possible to launch it directly through ranked matching. Popular content can rotate regularly, while very popular content can stay.

Some games may be sister games. They have so much content that it is uploaded in several parts, but their player groups overlap heavily. These cases can get special treatment, or the creator can apply for it. Games should not be tied to specific scenes either. Players can choose the terrain to load during initialization. Old versions should also be allowed to some extent, with creators manually deciding which versions remain usable.

## 4. Reports, chat, and the interface

The platform needs reports and muting, including muting within a match. Several players can vote to mute someone, or the host can do it, provided the gameplay does not depend on chat.

Chat can be split into ordinary chat and more simulated chat fully controlled by the creator, with colors to tell them apart. The second type can show words above characters' heads or limit them by distance. Voice can work similarly, though most game types do not need it. Chat should be global by default, rather than limited to the team. Playing games is often literally about chatting, especially in niche games.

In a first-person game, the lobby should be an actual hall with things to interact with. The UI should not feel slow. Common functions should be at the top level, and UI locations should not change often.

A gaming platform has another benefit: isolating EXE/Lua keeps users from downloading and running unsafe content.
